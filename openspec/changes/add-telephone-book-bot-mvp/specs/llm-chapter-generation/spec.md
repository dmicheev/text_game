# LLM-Chapter-Generation Specification

## Purpose

Генерация глав и резюме через LLM: контекст O(1) (не растёт с числом глав),
структурированный ответ, жёсткая валидация резюме, мягкая — объёма главы.

## Requirements

### Requirement: Структура запроса

**User Story:** Как система, я хочу фиксированный промпт на игру и короткий
контекст на ход, чтобы стоимость хода не зависела от длины книги.

#### Acceptance Criteria

1. System-промпт SHALL содержать снапшот стилевой карточки + правила
   (глава N из M, ~X слов, продолжение по резюме, без пересказа,
   «не заканчивай» для промежуточных глав)
2. User-промпт SHALL содержать только: тему, резюме предыдущей главы,
   пожелание автора (если есть), номер главы
3. Полный текст предыдущих глав SHALL НЕ передаваться в LLM
4. Провайдер SHALL быть сменяемым через конфиг (OpenAI-совместимый API)

#### Scenario: Запрос хода

1. Orchestrator вызывает build_chapter_messages(style_card, topic, summary, twist, n, m)
2. Провайдер отправляет запрос с response_format json_object
3. Ответ: {"title", "chapter", "summary"}

### Requirement: Валидация ответа

#### Acceptance Criteria

1. Резюме SHALL содержать ровно N слов (настройка игры); при нарушении —
   1 регенерация, затем принудительная обрезка до N слов
2. Глава SHALL быть в пределах ±20% от целевых слов; при нарушении —
   1 регенерация, затем принимается как есть
3. Некорректный JSON SHALL вызывать 1 повторный запрос
4. При недоступности провайдера система SHALL уведомить автора хода
   и оставить ход за ним (повторная попытка без штрафа)
